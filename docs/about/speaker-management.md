# Speaker Management System

## Overview

The `SpeakerManager` is the primary orchestrator for all speaker profile operations. A "Speaker" in `moves` represents the complete association between a presentation, its transcript, and the AI-generated alignment data. The manager provides comprehensive lifecycle management from creation through deletion.

## Speaker Profile Architecture

### Data Storage Structure

Each speaker profile resides in a dedicated subdirectory within `~/.moves/speakers/`:

```
~/.moves/speakers/
├── <speaker_id_1>/
│   ├── speaker.json          # Profile metadata
│   ├── presentation.pdf      # Local copy of slides
│   ├── transcript.pdf        # Local copy of speech text
│   └── sections.json         # Processed alignment data (when ready)
├── <speaker_id_2>/
│   └── ...
```

### Speaker ID Generation

Each profile receives a unique identifier generated by `id_generator`:

**Format:** `name-slug-xxxxx`

**Components:**
- **Name slug:** URL-safe version of speaker name
  - Lowercase conversion
  - Unicode normalization (NFKD)
  - ASCII transliteration (é → e)
  - Special character removal
  - Hyphen separation
- **Random suffix:** 5-character cryptographic random string
  - Ensures uniqueness even for identical names
  - Generated via `secrets` module
  - URL-safe character set

**Examples:**
- "John Doe" → `john-doe-a7k3m`
- "María García" → `maria-garcia-x9p2q`
- "Dr. Smith" → `dr-smith-b4n8t`

### Profile Metadata (`speaker.json`)

**Structure:**
```json
{
    "name": "John Doe",
    "speaker_id": "john-doe-a7k3m",
    "source_presentation": "/home/user/documents/presentation.pdf",
    "source_transcript": "/home/user/documents/transcript.pdf"
}
```

**Fields:**
- `name`: Human-readable speaker identifier
- `speaker_id`: Unique system identifier (directory name)
- `source_presentation`: Absolute path to original presentation PDF
- `source_transcript`: Absolute path to original transcript PDF

**Purpose:**
- Links speaker to source files for re-processing
- Enables file path updates without data loss
- Provides metadata for speaker listing and display

### Processing Status Indicators

**Speaker State:**
- **Pending:** Profile created, files referenced, `sections.json` absent
- **Ready:** Processing complete, `sections.json` present, can control presentations

**Status Determination:**
```python
is_ready = (speaker_path / "sections.json").exists()
```

## Core Operations

### 1. Creation (`add`)

**Purpose:** Create new speaker profile with presentation and transcript files

**Process:**

1. **Validation**
   - Verify speaker name doesn't conflict with existing IDs
   - Check source file paths exist and are readable
   - Ensure PDF format (implicit via later processing)

2. **ID Generation**
   - Generate unique `speaker_id` from name
   - Check for collisions (handled by random suffix)
   - Create speaker directory: `~/.moves/speakers/<speaker_id>/`

3. **Metadata Serialization**
   - Create `Speaker` dataclass instance
   - Convert `Path` objects to strings for JSON compatibility
   - Write `speaker.json` with formatted output (indent=4)

4. **Return Value**
   - Return `Speaker` object for immediate use
   - Provides confirmation to CLI layer

**CLI Command:** `moves speaker add "Name" ./slides.pdf ./transcript.pdf`

**Error Conditions:**
- Name conflicts with existing speaker ID
- Source files don't exist
- Insufficient permissions for directory creation

### 2. Modification (`edit`)

**Purpose:** Update source file paths for existing speaker profile

**Process:**

1. **Parameter Validation**
   - Accept optional `source_presentation` and/or `source_transcript`
   - Verify at least one parameter provided
   - Resolve paths to absolute paths

2. **Profile Update**
   - Load existing `Speaker` object
   - Update specified file path(s)
   - Preserve unchanged fields

3. **Metadata Persistence**
   - Serialize updated `Speaker` to JSON
   - Overwrite existing `speaker.json`
   - Maintain formatting (indent=4)

4. **Processing Implications**
   - Updated paths require re-processing
   - Existing `sections.json` becomes stale
   - User must run `moves speaker process` again

**CLI Command:** `moves speaker edit "Name" -p ./new_slides.pdf -t ./new_transcript.pdf`

**Use Cases:**
- Presentation content updated
- Transcript revised or corrected
- Files moved to new location
- Wrong files initially specified

### 3. Processing (`process`)

**Purpose:** Execute AI-powered data preparation pipeline for speaker(s)

**Asynchronous Architecture:**

**Why Async?**
- LLM API calls have significant latency (2-30 seconds)
- Multiple speakers can be processed concurrently
- CPU-intensive operations benefit from parallel execution
- Non-blocking design improves user experience

**Implementation:**
```python
async def process(speakers: list[Speaker], llm_model: str, llm_api_key: str):
    # Concurrent processing using asyncio
    tasks = [process_single_speaker(speaker) for speaker in speakers]
    results = await asyncio.gather(*tasks)
    return results
```
**Processing Pipeline:**

**Phase 1: File Resolution**

Determines which files to use for processing:

1. **Check Source Files**
   - Verify `source_presentation` path exists and is readable
   - Verify `source_transcript` path exists and is readable

2. **Check Local Copies**
   - Check for `presentation.pdf` in speaker directory
   - Check for `transcript.pdf` in speaker directory

3. **File Selection Logic**
   - **Priority 1:** Use source files if valid
   - **Priority 2:** Use local copies if source invalid
   - **Error:** Fail if neither source nor local files available

4. **File Copying**
   - Copy source files to local directory if using source
   - Overwrite existing local copies
   - Ensures local cache is current

**Phase 2: Pipeline Invocation**

Execute data preparation with thread isolation:

1. **Thread Isolation**
   - LLM call runs in separate thread via `asyncio.to_thread`
   - Prevents blocking the asyncio event loop
   - Enables true concurrent processing of multiple speakers

2. **Section Generation**
   - Call `section_producer.generate_sections()`
   - Pass presentation, transcript, model, and API key
   - Receive validated list of `Section` objects

3. **Result Persistence**
   - Serialize sections to `sections.json`
   - Mark speaker as "Ready" for presentation

**Phase 3: Result Reporting**

Create `ProcessResult` object with metadata:

```python
ProcessResult(
    section_count=len(sections),
    transcript_from="SOURCE" if used_source_transcript else "LOCAL",
    presentation_from="SOURCE" if used_source_presentation else "LOCAL"
)
```

**CLI Commands:**
- `moves speaker process "Name"` - Process single speaker
- `moves speaker process "Name1" "Name2"` - Process multiple
- `moves speaker process --all` - Process all speakers

**Performance:**
- Serial processing: ~5-30 seconds per speaker
- Parallel processing: Concurrent execution reduces total time
- LLM latency is primary bottleneck

### 4. Resolution and Lookup (`resolve`)

**Purpose:** Find speaker profile from user-provided string (name or ID)

**Resolution Strategy:**

**Step 1: ID Exact Match**
```python
if user_input in [speaker.speaker_id for all speakers]:
    return matched_speaker
```
- Fastest resolution path
- Deterministic and unambiguous
- Bypasses name ambiguity issues

**Step 2: Name Match**
```python
matched_speakers = [s for s in speakers if s.name == user_input]
```

**Sub-cases:**
- **Single match:** Return the speaker
- **Multiple matches:** Raise error with disambiguation prompt
- **No matches:** Raise error with "not found" message

**Ambiguity Handling:**

When multiple speakers share a name:
```
ValueError: Multiple speakers found matching 'John Doe'. Be more specific:
    John Doe (john-doe-a7k3m)
    John Doe (john-doe-x9p2q)
```

User must then use the unique ID:
```bash
moves speaker show john-doe-a7k3m
```

**Error Messages:**
- Clear indication of the problem
- Actionable guidance (show IDs for disambiguation)
- Consistent format across all CLI commands

### 5. Listing (`list`)

**Purpose:** Display all registered speaker profiles

**Process:**

1. **Directory Scan**
   - Enumerate all subdirectories in `~/.moves/speakers/`
   - Each directory represents one speaker profile

2. **Metadata Loading**
   - Read and parse each `speaker.json`
   - Deserialize to `Speaker` objects
   - Handle corrupted files gracefully (skip or error)

3. **Status Determination**
   - Check for `sections.json` existence
   - Mark as "Ready" or "Pending Processing"

4. **Return Value**
   - List of `Speaker` objects
   - Ordered by directory scan (filesystem-dependent)
   - Can be sorted by name or ID in CLI layer

**CLI Output Format:**
```
Registered Speakers:
  1. John Doe (john-doe-a7k3m) - Ready
  2. Jane Smith (jane-smith-x9p2q) - Pending Processing
```

### 6. Deletion (`delete`)

**Purpose:** Permanently remove speaker profile and all data

**Process:**

1. **Speaker Resolution**
   - Use `resolve()` to find speaker from name or ID
   - Handle ambiguity if needed

2. **Directory Removal**
   - Delete entire speaker directory recursively
   - Removes: `speaker.json`, PDFs, `sections.json`
   - No confirmation prompt (CLI handles this)

3. **Irreversibility**
   - Operation cannot be undone
   - All processed data is lost
   - Source files (outside `~/.moves`) remain intact

**CLI Commands:**
- `moves speaker delete "Name"` - Delete single speaker
- `moves speaker delete "Name1" "Name2"` - Delete multiple
- `moves speaker delete --all` - Delete all speakers

**Safety Considerations:**
- CLI should prompt for confirmation
- Display what will be deleted
- Particularly important for `--all` flag

## Data Integrity

**Atomicity:**
- Individual operations are atomic (success or failure)
- File writes use temporary files + rename for atomicity
- Directory creation is atomic via `mkdir(exist_ok=True)`

**Consistency:**
- `speaker.json` is source of truth for metadata
- `sections.json` presence indicates processing completion
- File paths in metadata may become invalid (user responsibility)

**Error Handling:**
- JSON parsing errors handled gracefully
- Missing files reported with clear messages
- Partial failures in batch operations reported individually
